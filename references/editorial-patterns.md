# Editorial patterns

Use these as optional structures. Vary them and let the topic determine the shape. Treat all examples as constructed copy, not the user's lived experience.

## Practical observation

Name a recognizable situation, explain the mechanism, then offer a small decision rule.

Example:

> A SaaS demo can impress everyone and still sell nothing.
>
> Before adding another feature, ask which step the buyer would stop doing if they bought it.
>
> If the answer is vague, the demo needs a clearer job.

## Small process

Give a short sequence the reader can use immediately. Include why the sequence matters; avoid listing generic advice.

Example:

> Before adding another AI agent, trace one failed task.
>
> Where did it lose the goal, the data, or the permission to act?
>
> Fix that handoff first. Another agent can inherit the same confusion with impressive confidence.

## Tradeoff

Show when each choice helps and make the deciding condition explicit. Avoid a universal winner.

Example:

> Automation helps when the steps are stable. A checklist helps when you're still discovering the steps.
>
> Automating too early is a lovely way to repeat a mistake at scale.

## Distribution insight

Connect visibility to a concrete buyer context or action. Explain where attention becomes intent.

Example:

> “We need distribution” is difficult to act on.
>
> “Our buyer asks for recommendations in three communities before buying” gives you somewhere to start.
>
> Map the decision before choosing the channel.

## Evidence-led longer post

Use a supported observation, the mechanism, one example, a limitation, and a practical takeaway. Mark hypothetical examples explicitly. Expand only when each paragraph adds value. Verify news and numbers before publication.

## Repair generic copy

| Weak draft pattern | Repair |
| --- | --- |
| AI is changing everything | Name one task, the failure it causes, and the changed workflow |
| Most founders get this wrong | State the specific decision and what makes it difficult |
| Ten tools you must use | Explain a job and selection criteria; use a list only if the comparison helps |
| Great point! Totally agree | Add a relevant counterexample, mechanism, or useful question |
| Comment YES for the secret | Give the useful idea directly; use an honest resource invitation only when relevant |
| An unsupported personal success story | Use supplied evidence or recast as a clearly hypothetical example |

## Batch variety

Distribute a batch across distinct premises, such as a workflow failure, a buyer decision, a technical tradeoff, a useful process, and a founder observation. Avoid five versions of “stop adding features.” Keep humor directed at situations rather than people. Do not make every ending a punchline.
